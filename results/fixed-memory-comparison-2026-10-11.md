# Fixed memory comparison — 2026-10-11

This is one bounded observation, not a speed or quality benchmark. Bays ran the same `art-quiet` profile, 90-minute budget, and three fictional sight leads through four `DecisionService` implementations. [The captured input](../benchmarks/fixed-art-quiet.json) fixes the candidate and normalized Dice facts; the [CSV](fixed-art-quiet-2026-10-11.csv) records each answer and timing. SHA-256 input hashes matched for all four engines. The cases are synthetic and nonsensitive.

| Engine | Runs / warmups | Mixed + classification calls | Typed failures | Choices in gallery / science / garden order | Research lead | Embabel process time |
| --- | ---: | ---: | ---: | --- | --- | ---: |
| Java rules (offline control) | 1 / 0 | 3 + 3 | 0 | prefer / pass / consider | Pocket Art Gallery | 58 ms |
| TypeSafe Jev `jev-1.13.0` | 1 / 0 | 3 + 3 | 0 | prefer / pass / consider | Pocket Art Gallery | 1,314 ms |
| OpenAI `gpt-4.1` | 1 / 0 | 3 + 3 | 0 | prefer / pass / consider | Pocket Art Gallery | 6,684 ms |
| CLEF 0.6B, local derived L1024 CPU | 1 / 0 | 3 + 3 | 0 | consider / consider / consider | none | 8,815 ms |

All four returned the expected **typed setting classifications**: indoor / indoor / outdoor. All four classified the gallery's `interest-match` proposition true and the other two false. Jev rated the garden `strong` where the Java rules and GPT-4.1 rated it `possible`. CLEF rated all three `weak`; the local ranker therefore admitted no research lead. That is a validity difference, not an operational failure. No answer was silently replaced with rules output. The hard eligibility checks were identical and all three fixed sights were eligible.

The application measured each `DecisionService` call with `System.nanoTime()`. The per-call values are in the CSV. The **process time** spans Embabel process execution, Dice reads, decisions, and local ranking; it excludes JVM startup and Spring initialization. Remote Jev and OpenAI call times include client overhead, network, service queueing, model computation, and response parsing. They are not pure model inference measurements. CLEF call time includes serialization and a fresh Python checker subprocess for each request; [its logged model-inference and bridge-wall observations](clef-probabilities-2026-10-11.json) separate those stages. CLEF's first mixed call spent 4,166 ms in the bridge with 564 ms reported model inference, consistent with substantial first-load overhead. Later bridge calls were about 0.8–0.9 seconds. The process used a locally repacked, single-function L1024 CPU bundle because the published multifunction bundle did not load directly on this host. [Provenance and hashes](clef-derived-provenance-2026-10-11.json) and [reproduction steps](../clef/README.md) describe that local variant; model weights are not committed.

To reproduce the fixed run after `mvn test package`, use `benchmarks/run-fixed.sh local` or `jev`, `openai`, or `clef`. The remote engines require the corresponding existing process-environment API key. CLEF requires a prepared local model bundle and checker via `CLEF_MODEL_DIR` and `CLEF_CHECKER_PATH`. The script runs one profile and three candidates, sets one LLM attempt, and checks the input hashes. No remote run is needed for tests or the default app. All observations can change with host load and provider conditions; one un-warmed run provides no reliable latency ordering.
