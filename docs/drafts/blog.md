# Jev and Embabel - Bayes of our Lives

TypeSafe calls [Jev a System One model](https://typesafe.ai/blog/introducing-system-one-models-and-jev). Give it the facts of a situation and a bounded question, and it returns a typed answer. We added decision and classification requests to Embabel Agent so an agent can use those answers while it works toward a goal. Result quality and execution times may vary.

Suppose we land in a city with a little time to spare. We could see something, find breakfast or lunch, or keep looking until a better option turns up. A list of nearby places is a start. A useful suggestion also has to account for the time available and the kind of stop we would enjoy. We built **Bays**, a small Java city guide, to give Embabel Agent that job.

The part we wanted to get right is memory. Bays stores fictional traveler preferences in [Dice](https://github.com/embabel/dice), retrieves them for the outing, and puts validated preference fields into the **decision request itself**. The model sees the venue facts alongside what this fictional traveler likes. The application keeps the fact IDs so we can tell which memory informed an answer. Raw memory prose never becomes a model instruction, and the ranker does not go back to Dice for a bonus after the answers arrive. The default Dice store is in memory; a separate optional Neo4j run verified graph retrieval and normal cleanup.

## A short outing with a memory

The repeatable example uses a fictional city, Harborview, and three possible sights: Pocket Art Gallery, Hands-On Science Hall, and Riverside Garden. Its fictional `art-quiet` traveler has 90 minutes, likes art and quieter places, and is comfortable with a short drive. Bays retrieves that profile, discovers the three leads, checks the hard time and source requirements, and asks a selected decision backend about each eligible place. Embabel plans those actions and carries their results toward a provisional research lead.

Each typed request has a job. A **proposition** asks whether the venue's supplied interest tag matches the retrieved interest. A **choice** says `prefer`, `consider`, or `pass` based on interest, ambience, and drive comfort. A **rating** describes the strength of that fit as `strong`, `possible`, or `weak`. A separate **classification** names the supplied setting as indoor, outdoor, or unknown; it does not choose the outing. Application code handles the hard time and source checks. A local Embabel ranker orders only leads the typed answers admitted. This lets us change the decision model while keeping the agent's actions and eligibility rules in view.

We ran the same three fictional sights and normalized Dice context through **Jev**, **OpenAI `gpt-4.1`**, and **local CLEF 0.6B**. The captured decision-input hashes matched across the backends. Jev and gpt-4.1 answered `prefer` for Pocket Art Gallery, and the ranker put it first. CLEF returned valid typed answers, but rated all three leads `weak`; the application returned **no research lead**. That is a useful result. A valid answer can still leave the agent without an acceptable recommendation, and Bays shows that outcome instead of quietly replacing it with an answer from another engine. Transparent Java rules ran as an offline control, not a fourth model.

CLEF is experimental here. The published multifunction Core ML package would not load on the test host, so the local adapter used a derived single-function package that preserves the model graph and weights, with CPU execution. We ran each backend once without warmup. The observed elapsed times include very different network, loading, and bridge costs, so they do not establish a model speed ranking or a general quality order.

Bays can also look for mapped sights or restaurants in a requested city. That path uses public place, geocoding, and base-route data and may find fewer than three leads. A word in a venue name is only a tentative interest tag; it does not establish what the place is like. Opening hours, admission, accessibility, cuisine, dietary safety, and live traffic are not verified. The output stays a **research lead**, not a booking or a promise that a stop will work today. The fixed Harborview comparison is the controlled demonstration of model behavior; the live lookup is the way to start investigating a real city.

This is what makes the small example useful to developers: we can see the facts the agent gathered, the Dice memory it accepted, the exact kind of question it asked, and the effect of each model's answer on the next step. Change the backend and the planning flow stays put. Change the memory and the decision gets new context before anyone ranks a list.

Result quality and execution times may vary. Consult your app configuration for requests lasting longer than one minute. For best results use the right model for the right job. Embabel Agent the right tool for your agentic APIs.
