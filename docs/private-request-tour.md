# Decision request tour and Tripper adaptation

The live agent accepts an unrestricted destination and optional origin. `TripDataProvider` supplies actual location, mapped place leads, forecast weather and marine values, and an optional base driving route. `PaddleComparisonAgent.gather` turns those into typed per-place briefs. The same `assess → preferences → rank → finish` actions produce a goal card containing a place and proposed UTC window. A card backed by missing station tide datum, access, or traffic is marked `research`.

This adapts the structure of Tripper's [`JourneyTravelBrief`, `PointOfInterest`, and `TravelPlan`](https://github.com/embabel/tripper/blob/main/src/main/kotlin/com/embabel/tripper/agent/domain.kt) and its [`findPointsOfInterest`, `researchPointsOfInterest`, and goal actions](https://github.com/embabel/tripper/blob/main/src/main/kotlin/com/embabel/tripper/agent/TripperAgent.kt). I also inspected Tripper's `ToolsConfig.kt`, `Brave.kt`, and `application.yml`: its broad web/maps/weather tool groups and Brave search are not configured here, so this bounded CLI uses documented public APIs instead. No Tripper source was copied. Tripper is Apache-2.0 licensed and is credited in the README.

The resolved Embabel Agent `1.5.4-SNAPSHOT` API has exactly three `QuestionKind` values: `PROPOSITION`, `CHOICE`, and `RATING`. `DecisionSpec.builder()` makes the mixed `DecisionRequest` used once per candidate. A direct `PropositionRequest` is covered in local tests. Classification is a separate `ClassificationRequest` and `ClassificationService.classify` call. `Ranker.rank` orders eligible or explicitly provisional candidate objects. There is no `RankRequest` or `QuestionKind.RANK` in this resolved version. Jev and OpenAI supply typed assessment and classification evidence, while this app implements a local, transparent `Ranker` for every engine mode.

Jev's rating adapter can return a distribution and expected-level-index score without a selected level. The app preserves that raw state and locally projects a level only if one distribution probability is strictly above 0.5. The guard never converts unknown tide datum, access, or traffic into verified suitability. In live mode the local ranker may order forecast-backed **research leads** with an explicit `research` goal status. In fixture mode it ranks only records that satisfy the complete synthetic local policy and typed evidence; the top one has `candidate` status.

`--demo.mode=compare` is the **offline synthetic test catalog** and alone recognizes Miami, Charleston, Savannah, and NYC. Its fictional date, places, readings, traffic, daylight, and preferences must not be described as live. `--demo.mode=live` accepts any destination that geocoding can resolve. A place search can return zero nearby launch leads; the fallback is a named forecast area, not a fabricated launch. Optional `--demo.dice.enabled=true` starts an owned disposable Neo4j container, saves four fictional preference propositions through Dice 0.4.0, and reads them for ranking. The graph-backed profile was verified in local fixture and Miami runs; it contains no personal facts.

Live providers: [Open-Meteo geocoding](https://open-meteo.com/en/docs/geocoding-api), [OSM Nominatim search](https://nominatim.org/release-docs/latest/api/Search/) under its [public usage policy](https://operations.osmfoundation.org/policies/nominatim/), [Open-Meteo weather](https://open-meteo.com/en/docs), [Open-Meteo marine](https://open-meteo.com/en/docs/marine-weather-api), and optional [OSRM route](https://project-osrm.org/docs/v5.24.0/api/). OSM place data: © OpenStreetMap contributors, ODbL. A marine model's MSL sea level is not an MLLW tide prediction, and model-grid current is not a local station current. The route estimate excludes live traffic.
